# Self-learning loop (pre-registered 2026-11-17, requested by Rayyan: positive reinforcement and self-learning are fundamental)
Deterministic code only (zero Claude at runtime). Parameters stay frozen per version; the engine adapts ONLY through this scheduled, evidence-gated loop.

1. **Record** every trade with its path (best / worst point) and a plain-English review (History tab).
2. **Shadow-replay** (daily 21:20 GMT): every finished, filled live trade is replayed under the frozen exit and under 9 candidate exit rules (A1-A3 break-even, B1-B3 trailing,
   C1-C3 keep-a-share), same prices, same tracker. Stored in `shadow`.
3. **Reinforce**: a scoreboard of paired gains/losses (rule minus frozen, R) on NEW trades only, with clustered confidence ranges.
4. **Promote** (Friday review, announced on Telegram) a rule for NEW setups only if ALL hold: >= 60 finished live trades; lower bound of its clustered CI > 0 at alpha 0.05/9;
   the offline walk-forward exit test (docs/results/exits.json) chose the SAME rule and passed on unseen history under both cost models; no promotion/rollback in the last 14 days.
   The setup keeps the exit rule it was published with (stored in its immutable record). Only stop-TIGHTENING rules are eligible, so no trade can lose more than its original stop.
5. **Roll back** automatically (announced) if the champion's own forward trades (>= 40) have a CI upper bound < 0 versus the frozen exit.
6. Entries, filters, targets and sizing are NOT auto-changed: they need a pre-registered offline test and Rayyan's go-ahead.
7. Every decision is logged (`learning_log`, docs/results/learning.md). Alerts: PROMOTED / ROLLED BACK / PROFIT PROTECTED (first stop move per trade).

## No bottlenecks (lesson from the old engine: stacked vetoes meant it stopped trading)
- Entry filters: at most 2 conditions per rule, each chosen filter must keep >= 40% of historical trades, and none is applied without passing validation AND a deliberate, announced switch (ops/filters.json).
- Throughput guard (weekly review): if filters remove more than 50% of candidates over 7 days (>= 6 candidates seen), they are switched off automatically and Rayyan is told.
- Setup frequency is measured, not assumed: the dashboard/Telegram weekly note reports published vs filtered counts.

## Strategy scorecard and probation (pre-registered 2026-11-26, owner request: act on failing strategies, reinforce successful ones)
Code: src/fxengine/learn/scorecard.py. Fixed BEFORE it could act on any result: LEARNING under 15 finished live trades; WEAK = 15+ trades and shrunk mean (n/(n+30) x mean) below -0.25R; CONFIRMED = 30+ trades and the 95% range of mean R entirely above 0; SUSPENDED = 30+ trades and the range entirely below 0.
Effects: SUSPENDED strategies are still published and scored (research and forward test untouched) but not taken in the GBP 2,500 account (lots_account = 0, marked suspended); recomputed from all live trades each time, so reversible. CONFIRMED and WEAK change labels only (dashboard card, weekly Telegram note). No strategy rule, gate or parameter changes. First cash priority for CONFIRMED strategies is NOT built: it would change which setups reach the account and needs its own pre-registration.
Honest limit: with about 5 setups a day over several strategies, the first strategy can reach 30 trades in roughly two to four weeks, so no switch-off is expected before then.

## Live post-mortem and the road to self-learning filters (spec 2026-11-26, refined after an independent audit of the plan)
**Built now (information only, changes nothing):** src/fxengine/learn/postmortem.py, written daily after the 21:20 learning job to docs/results/postmortem.md, shown as a dashboard card, 3-line Telegram note on Fridays.
- Loss anatomy per losing trade, from its own path (outcomes.mfe_r): WRONG FROM THE START (never more than +0.4R ahead), FADED (reached +1R or better, then lost), TIME-OUT, other.
- Separators: each of the 12 pre-registered entry conditions (learn/filters.py ATOMS) compared on trades that PASS versus FAIL it (win rate, mean R, Welch z, two-sided p), pooled and per strategy.
- Multiple-testing correction (named): m = every comparison attempted in the report (12 per group, groups = pooled + each strategy with 16+ trades). SUPPORTED needs 30+ trades on each side AND p <= 0.05/m (BONFERRONI, family-wise error 5% for the whole report). HYPOTHESIS needs 8+ each side and BENJAMINI-HOCHBERG false-discovery 10% over the same m; display only. Ranges shown are Bonferroni-corrected. (An earlier draft used a constant that corresponded to 0.05/6; it was wrong and is replaced by the computed value.)
- Tests: 30 pure-noise datasets produce at most 2 SUPPORTED findings in total; a realistic planted effect (win rate 48% vs 33%, about 0.45R) is found only with about 1,500 trades and NOT with 24; the 3-line note, the loss anatomy and the stated Bonferroni threshold are checked. Honest consequence: real, modest effects need hundreds to thousands of trades to become SUPPORTED, so for weeks the report will mostly show hypotheses.
**Definitions (for the audit):** "shadow replay" (learn/review.py shadow_one) replays the WHOLE finished setup through the same tracker used live (track_arrays on M5 bid/ask bars, cost model on) with a candidate exit hook, and stores the resulting net R; it never re-scores a single bar. The 60-trade gate for exit promotion counts paired finished trades POOLED over all strategies (scoreboard n), not per strategy. The throughput guard (filters off if more than 50% of candidates were removed in 7 days, 6+ candidates) is POOLED over all strategies today; a per-strategy guard is part of item D below because a pooled guard would let one strategy be starved.
**Scorecard/probation (built):** per strategy, from finished live trades: LEARNING under 15 trades; WEAK = 15+ trades and shrunk mean (n/(n+30) x mean) below -0.25R (label only); CONFIRMED = 30+ trades and the 95% range of mean R above 0 (label only); SUSPENDED = 30+ trades and the 95% range below 0. SUSPENDED = new setups of that strategy are still published and scored but not taken in the GBP 2,500 account (lots_account = 0); recomputed every time, so reversible. It is a mean-R test, not a win-rate test.
**Item D (NOT built; needs the owner's explicit go-ahead; build only after A and B have run on real data):** automatic entry filters. A condition is applied only if (1) it is SUPPORTED live (30+ trades each side, Bonferroni as above), (2) it also passed the offline entry-filter validation on unseen history (existing study, same thresholds, nothing new), (3) it removes less than 50% of THAT strategy's candidates over 7 days (per-strategy throughput guard), (4) no other filter change in the last 14 days. Every application is logged to learning_log (kind FILTER_APPLIED) and docs/results/filters_applied.md with: timestamp, strategy, condition, live evidence (n each side, mean R each side, difference, corrected range, p, m), history evidence (study numbers), share of candidates removed in the last 7 days; announced on Telegram. Veto: ops/filters_veto.json (version-controlled) or the owner telling the engineer; vetoed filters are never re-applied. Automatic removal if the filter's own forward trades show its pass group doing WORSE (SUPPORTED, same test) or the guard trips.
